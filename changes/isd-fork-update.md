### Added

- A fork of another version of an open ISD updates its IED instead of being refused: `report` and `apply` with `verb: 'ied'`, `scenario: 'fork'` on an ISD document holding the source IED's `uuid`, and `tx.lifecycle.update.ied` with the new `scenario` option (`UpdateIedParams['scenario']`: `'template'`, the default, or `'fork'`). Elements pair by `uuid` (a rename is one change), names and values follow the other version, an element only in the open ISD is `target-only` and kept by default, and nothing is written in the `Header` or `IEDSourceFiles`. The `Communication` section is reported as an instance of its own and written as its groups decide. The specification beside the IED is reported and written with it, paired by `uuid` (a function or an application only in the open ISD `target-only`, kept by default), and the types the IED and the specification share follow the other version under their own ids; an `LNode`'s specified naming follows. A fork of the file itself (both `Header`s naming the same file) re-targets references the other version points elsewhere (an `LNode`'s binding, a `SourceRef`'s source), written by uuid and named by the commit; a re-target waits for the group adding its target, and one onto nothing the fork holds keeps its target with a new warning, `reference-retarget-unresolved` (`ReportWarning`). A fork into a project keeps the references the project made. A function an application stops composing that the same update holds as a standalone function is updated as such instead of removed. A fork into a project holding the IED is still refused.
